# 闭环 MVP 路线

## 1. 什么叫“每一步闭环”

本路线中的每个 MVP 都必须同时具备：

1. **用户入口**：页面、接口或明确可运行的脚本。
2. **真实处理**：不是只有静态页面或孤立函数。
3. **可见结果**：用户能看到成功、失败和进度。
4. **状态收口**：每次运行最终进入 completed、failed、cancelled 或 waiting 等明确状态。
5. **自动验证**：至少有无需真实模型的确定性测试；涉及模型的步骤另有显式开启的真实模型测试。
6. **操作说明**：README 写明启动、体验、常见错误和验收方法。

完成一个 MVP 后再进入下一个，后续能力只在已通过的闭环上增量叠加。

## MVP-0：全新工程与模型连通性

### 目标

从零创建独立 Web、API 和契约包，证明新项目没有依赖旧业务目录，并能安全验证模型是否可用。

### 实施内容

- 创建新的三个 workspace 和启动脚本。
- 新服务独立实现模型工厂，只读取允许的模型环境变量。
- 提供 liveness、readiness 和模型诊断接口。
- Web 页面显示 API、模型、tool calling 能力的诊断结果。
- 错误信息区分：API 不通、密钥缺失、provider 不通、模型不支持工具调用。

### 闭环演示

打开新页面，点击“检查模型”，页面显示所选模型和一次最小 tool-call 探测结果；服务端输出带 traceId 的诊断日志，但不输出密钥。

### 验收

- 不配置 key 时，页面明确提示缺少配置，API 不崩溃。
- 配置有效 key 时，诊断成功。
- 仓库扫描确认新 workspace 没有 import `services/chat`、`services/deepagent-api`、`clients/deepagent-web` 或旧 contracts。
- build、typecheck、协议测试和 Browser smoke 全部通过。

### 本阶段不做

不创建业务 Agent，不接数据库，不复制旧页面。

## MVP-1：单需求 DeepAgent 分析

### 目标

完成第一条真正的业务竖切：用户输入一条信息完整的需求，DeepAgent 输出一份可查看的分析报告。

### 实施内容

- 创建 root Agent 和 `requirement-analyst` 子 Agent。
- root Agent 使用 `write_todos` 规划，使用 `task` 委派。
- 子 Agent 输出需求摘要、完整性、风险、复杂度、用户故事和验收标准。
- 建立 POST 流式接口和最小业务事件协议。
- Web 展示输入、执行轨迹、最终 Markdown 和本次产物。
- 支持 AbortSignal 取消，所有异常转换为公开错误事件。

### 闭环演示

输入“批量导入 Excel，最多 10,000 行，失败记录可下载，操作保留审计日志”，页面先出现运行和计划事件，随后显示最终报告，运行以 `run.done` 结束。

### 验收

- 一次成功运行有且只有一个开始事件和一个终态事件。
- 报告包含需求摘要、风险、用户故事和可验证的验收条件。
- 点击取消后服务端收到中止信号，运行状态为 cancelled，不再继续推送结果。
- StateBackend 中的 `/work` 产物能由业务导出器读出并返回 Web；不把虚拟路径误报为本机磁盘地址。
- stub model 测试覆盖事件顺序；真实模型测试需显式开关。

## MVP-2：信息澄清与同线程恢复

### 目标

让不完整需求也能闭环，而不是生成带有臆测的报告。

### 实施内容

- 定义结构化完整性结果和澄清问题 Schema。
- 当关键字段缺失时触发 `clarification.required`。
- 使用 checkpointer 保存等待状态。
- Web 渲染澄清表单并提交回答。
- 恢复接口校验 thread、run 和待处理问题后继续原任务。
- 用户拒绝或放弃时将运行收口为 cancelled。

### 闭环演示

输入“增加批量导入”，系统询问文件格式、数量上限、权限和失败处理；用户填写后，原运行继续并生成报告。

### 验收

- 澄清前不生成最终报告。
- 恢复后的报告包含用户补充内容，并保留原始需求。
- 重复提交同一回答不重复执行外部动作。
- 服务重启后的可恢复性先通过 checkpointer 集成测试验证；真正跨重启持久化在 MVP-4 完成。

## MVP-3：按需多专家协作

### 目标

把参考业务的功能、性能、安全、合规分析直接实现为 DeepAgent subagents。

### 实施内容

- 新建四个领域子 Agent，各自拥有独立 Prompt、工具白名单和固定输出契约。
- root Agent 根据需求选择专家并维护 todos。
- 专家结果写入各自独立虚拟文件，根 Agent 只读汇总。
- 业务事件适配器识别专家开始、工具调用、完成和失败。
- 支持并行执行；禁止多个专家并发写同一单值 channel 或同一文件。
- 设置专家超时、最大步骤和失败降级。

### 闭环演示

输入批量导入需求，root Agent 选择功能、性能和安全专家；页面分别显示进度，最后给出一份汇总报告和三份专家产物。纯文案需求不应无条件触发所有专家。

### 验收

- 专家选择与输入维度基本一致。
- 一个专家模拟失败时，其他结果仍能展示，报告明确标注缺失领域。
- 没有 `Invalid concurrent graph update`、重复委派或无限 `read_file` 循环。
- 每个专家产物路径唯一，最终报告只由 root Agent 写入。

## MVP-4：持久化会话、运行和产物

### 目标

把可运行 demo 变成重启后仍可使用的业务系统。

### 实施内容

- 建立 conversation、message、agent_run、todo、artifact 和审批记录。
- 使用持久化 checkpointer 保存 DeepAgent thread 状态。
- 将 VFS 工作文件显式导出到受控 artifact store；数据库保存元数据和访问地址。
- 实现会话列表、历史消息、运行详情和产物下载接口。
- Web 支持刷新页面后恢复历史和最终状态。

### 闭环演示

完成一次分析，重启 API，再次进入同一会话，仍能查看消息、执行结果、参与专家和下载报告。

### 验收

- 重启前后的数据一致。
- 产物只能由所属用户读取。
- 虚拟 `/work` 与持久化 artifact store 的映射有自动测试。
- waiting、completed、failed、cancelled 状态不会在重启后变成永远 running。

## MVP-5：知识上传、检索与引用

### 目标

让报告基于企业事实，而不是只依赖模型通用知识。

### 实施内容

- 支持上传产品说明、历史需求和规范文档。
- 实现解析、切分、向量化、索引和处理状态。
- 提供带租户过滤的混合检索工具。
- 把检索实现包装成 root/专家可调用的 DeepAgent tool。
- 报告保存来源文档、片段和检索摘要。
- 检索失败或超时可降级，但必须告知报告未使用企业知识。

### 闭环演示

上传“批量导入上限为 10,000 行”的内部规范，待处理成功后提交相关需求；报告引用该规范，并以它为依据生成性能与验收结论。

### 验收

- 上传到可检索状态的完整流程可见。
- 不同用户或租户无法互相检索文档。
- 删除文档后不再召回对应 chunk。
- 检索超时不会让 SSE 连接长期无任何响应。
- 至少有一组固定语料评测 Recall 和引用正确性。

## MVP-6：业务工具、MCP 与人工审批

### 目标

让 Agent 不只“写报告”，还能安全读取和更新业务系统。

### 实施内容

- 先实现本地只读工具：相似需求、性能基线、安全策略、合规矩阵。
- 为工具定义输入输出 Schema、超时、权限、审计和公开错误。
- 再通过 MCP adapter 接入同等能力，业务 Agent 不感知工具来源。
- 新增一个有副作用的示例动作，如“创建需求草稿”。
- 写动作通过 HITL 暂停，用户确认后才执行；拒绝则安全收口。

### 闭环演示

Agent 在报告后建议创建需求草稿，页面展示将写入的字段；用户批准后工具返回外部记录编号，页面和审计日志都能查看该结果。

### 验收

- 未授权工具不会出现在 Agent 可用工具集中。
- 不批准就不会产生外部写入。
- 重复批准请求通过幂等键只产生一次写入。
- MCP 不可用时，本地工具或明确降级路径生效。

## MVP-7：多需求长链与总体影响报告

### 目标

体现 DeepAgent 相比固定流程最有价值的场景：跨多个需求自主规划、分派、暂存和汇总。

### 实施内容

- 支持一批有明确编号的需求输入。
- root Agent 为每个需求建立 todo 和独立工作目录。
- 限制最大需求数、并发数、运行时长和 token 预算。
- 子任务可重试、跳过或从 checkpoint 恢复。
- 最终产物包含逐项结论、跨需求依赖、冲突、优先级和总体风险。

### 闭环演示

一次提交登录、百万行导出和后台审计三个需求，页面展示逐项分析和总体汇总；其中一个子任务模拟失败后，可单独重试并更新总报告。

### 验收

- 计划、子任务和最终报告可按 requirementId 追溯。
- 单项失败不丢失其他已完成结果。
- 超过上限时在执行前明确拒绝或要求拆批。
- root Agent 以总报告成功落盘作为完成条件，不因 todos 文案变化重复委派。

## MVP-8：安全、观测、评估与发布闭环

### 目标

完成可安全演示和持续迭代的生产基线。

### 实施内容

- 身份认证、租户隔离、输入守卫、工具权限和敏感字段脱敏。
- 结构化日志、trace、指标、token/成本、Agent 与工具耗时。
- 固定数据集评估完整性、专家路由、RAG、报告质量和安全拒答。
- Layer 1 确定性测试、Layer 2 可选真实模型、Layer 3 Browser E2E。
- CI 执行 build、typecheck、test、依赖和安全检查。
- 部署环境完成 readiness、SSE、持久化和回滚验证。

### 闭环演示

从浏览器登录、上传知识、澄清需求、完成多专家分析到下载报告，全链路产生可关联 trace；质量门未通过的版本不能进入部署阶段。

### 验收

- 测试环境完成最终端到端验收故事。
- API key、需求正文和敏感工具参数不出现在日志或前端诊断数据中。
- 注入攻击、越权读取、未审批写工具均被阻止。
- 关键质量、延迟、错误率和成本指标有基线和报警阈值。
- 发布失败有可验证的回滚路径。

## 2. 建议实施节奏

| 阶段 | 可独立体验的结果 | 进入下一阶段的硬条件 |
| --- | --- | --- |
| MVP-0 | 新页面完成模型诊断 | 新目录零旧业务依赖，构建和 smoke 通过 |
| MVP-1 | 单条完整需求得到报告 | 事件、取消、错误和产物全部收口 |
| MVP-2 | 不完整需求可澄清并恢复 | 同一 thread 恢复和幂等验证通过 |
| MVP-3 | 多专家按需协作 | 并发、失败隔离和终止条件通过 |
| MVP-4 | 重启后可查看会话与产物 | 数据归属与 checkpoint 一致性通过 |
| MVP-5 | 企业文档影响报告且有引用 | 隔离、删除、超时和检索评测通过 |
| MVP-6 | 审批后执行一次业务写动作 | 权限、审计和幂等通过 |
| MVP-7 | 多需求形成总体影响报告 | 限流、重试、部分失败和预算通过 |
| MVP-8 | 可观测、可评估、可部署 | 全链 E2E 和发布质量门通过 |
